# Spec: приём списка по HTTP и смета прогона до его старта

Вторая поставка Ф6, серверная её половина. Экран загрузки приезжает следующей;
здесь появляется то, чем его питать.

## Problem

Список доменов попадает в сервис только командой `run_collect.py intake`.
Загружают его PR-отдел и руководители — люди, у которых нет ни консоли, ни
доступа к серверу. Пока приёма по HTTP нет, «ручной запуск» из ТЗ означает
«позвать инженера».

Второе: **ТЗ требует показать смету до запуска и не дать запустить, если квоты
не хватает**. Смета сейчас считается внутри прогона, после того как строка
прогона уже открыта: узнать цену, не начав, нельзя. Экран «сколько это будет
стоить» питать нечем.

Третье — найдено осмотром перед поставкой. Окна точек (сколько месяцев истории
покупаем) читаются из активной версии порогов и передаются в сбор **только из
CLI**: `workers/jobs.py` зовёт `collect_projects` без `windows`, то есть прогон,
запущенный кнопкой, покупает не то же, что прогон из консоли. Смета, показанная
человеку, обязана быть ценой того прогона, который начнётся, — иначе экран врёт
о деньгах.

## In scope

- `POST /api/intake/file` — приём XLSX или CSV **телом запроса**, имя файла
  параметром. Право `run`.
- `POST /api/intake/link` — приём опубликованной Google Sheet по ссылке.
  Право `run`.
- Ответ приёма: сколько принято, создано, обновлено и **построчные отказы с
  причиной** — ТЗ требует «пропускать с пометкой + отчёт об ошибках».
- `GET /api/runs/estimate` — смета шага 1 по текущему набору проектов: units,
  число запросов, что уже в кэше, разбивка по схеме, остаток квоты, вердикт
  preflight и причина отказа. Право `read`.
- Один источник окон точек на всех: CLI, фоновая задача и смета берут их из
  активной версии порогов одинаково.
- Предел размера тела: файл на сто строк — это килобайты, и принимать
  двухсотмегабайтную книгу незачем.

## Out of scope

- **Экран загрузки** — следующая поставка (`web-intake`). Здесь только API.
- Приём в фоне: файл на сто строк разбирается за миллисекунды, очередь ему не
  нужна. Прогон в очереди уже есть и не трогается.
- Правка списка руками через интерфейс: ТЗ этого не просит, источник — таблица.
- Смета ступеней 2 и 3: дорогие метрики покупаются только прошедшим воронку, и
  до классификации их цена неизвестна.

## Acceptance examples

| # | Вход | Ожидаемый выход |
|---|---|---|
| E1 | XLSX с десятью годными строками | принято 10, созданы проекты, ответ называет число |
| E2 | файл, где одна строка без домена | годные приняты, битая отклонена с причиной и номером строки |
| E3 | тот же файл второй раз | обновлено, не удвоено |
| E4 | `.pdf` в теле | `400` «не понимаю источник», а не `500` |
| E5 | тело больше предела | `413` с названным пределом |
| E6 | ссылка на закрытую Google Sheet | `400` про страницу входа, а не «принято 0» (L10) |
| E7 | человек без права `run` | `403`, называющий право |
| E8 | смета при N проектах | `units_estimated` совпадает с тем, что посчитает прогон на тех же данных |
| E9 | квоты не хватает | `may_start=false`, вердикт `not_enough`, причина с числами |
| E10 | остаток квоты неизвестен | вердикт `unknown` отдельно от `not_enough` (L23), `may_start=false` |
| E11 | `GET /api/runs/estimate` | отвечает сметой, а не `422` от маршрута `/{run_id}` |
| E12 | прогон из очереди и смета | берут окна точек из одной активной версии порогов |

## Non-functional

- Смета не стоит units: план строится по базе, остаток квоты берётся запросом
  ценой 0 (в fixture-режиме — без сети).
- Приём проверяет всю таблицу до первой записи: сто строк не должны оставить
  базу наполовину заполненной из-за сороковой (свойство `accept`, сохраняется).
- Поставка укладывается в `max_loc_diff` 800 без waiver.

## Open questions

- Предел размера тела выбран нами (2 МБ): ТЗ ограничивает вход сотней проектов,
  а не байтами. Если отдел пришлёт книгу с картинками — упрётся, и текст ошибки
  скажет, во что именно.
