# Spec: вход в сервис — пароли, токены и права

Первая поставка Ф5. Сервис перестаёт быть анонимным: появляется вход, токен и
проверка прав на роутере.

## Problem

С Ф1 в зависимостях висит заглушка: `current_group` возвращает `user` всем.
Она сделана наименее правой нарочно, но это всё же заглушка — любой, кто дойдёт
до порта, получает права пользователя.

ТЗ называет три группы: инженер, админ, пользователь. Различие сейчас одно —
правка порогов, и это осознанно: список сотрудников заказчик ещё не прислал.
Но фиксировать надо три, потому что права разойдутся предсказуемо (пользователи,
ключи и лимиты — работа инженера, а не руководителя).

Есть и вторая, тихая беда: правило прав живёт **в двух местах** — таблицей в
`api/deps.py` и свойствами `can_*` у модели пользователя. Свойствами никто не
пользуется, и это худший вид дубля: он не расходится, пока на него не сошлются.

## In scope

- `api/security.py` — bcrypt для паролей, JWT для сессии: выпуск и разбор.
- `api/routers/auth.py` — `POST /api/auth/login` и `GET /api/auth/me`.
- `api/deps.py` — настоящий `current_user` из заголовка `Authorization`, группа
  из него же; `require_right` остаётся формой проверки, меняется источник.
- Удаление второй копии правила прав: свойства `can_*` у модели уходят, таблица
  прав остаётся одна.
- CLI `useradd` — первый пользователь должен откуда-то взяться; пароль
  спрашивается, а не передаётся аргументом.

## Out of scope

- **Роутеры данных** (проекты, прогоны, кейсы, пороги) — следующие поставки Ф5.
  Здесь только вход и проверка прав.
- Управление пользователями через API (право `manage_users` уже есть, экрана
  нет) — вместе с экранами Ф6 либо отдельной поставкой, когда понадобится.
- Сброс пароля, вторая фаза входа, SSO — ТЗ не требует.

## Acceptance examples

| # | Вход | Ожидаемый выход |
|---|---|---|
| E1 | верные почта и пароль | `200` с токеном, группой и списком прав |
| E2 | верная почта, неверный пароль | `401` и **та же** формулировка, что при неизвестной почте: ответ не подсказывает, какие адреса заведены |
| E3 | выключенный пользователь | `401`: выключить — значит закрыть вход, а не только спрятать из списка |
| E4 | запрос без токена к защищённому роутеру | `401` |
| E5 | испорченный или просроченный токен | `401`, и причина видна в логе, а не в ответе |
| E6 | токен пользователя на роутере с правом `edit_thresholds` | `403` с названием недостающего права |
| E7 | токен админа и инженера там же | `200` |
| E8 | пустой `JWT_SECRET` | токен не выпускается вовсе: подписанный пустым секретом подделывается |
| E9 | пароль в базе | хранится bcrypt-хешем; исходный пароль не восстановим и в логи не попадает |
| E10 | правило прав | живёт в **одном** месте: таблица групп и прав, а не копии у модели |

## Non-functional

- Пароль не логируется ни при входе, ни при ошибке.
- Хеширование стоит денег по времени нарочно: bcrypt с рабочим фактором по
  умолчанию (~0,25 с на проверку) — это защита, а не расход.
- Поставка укладывается в `max_loc_diff` 800 без waiver.

## Open questions

- Список сотрудников с группами заказчик обещал, но не прислал. До него
  пользователи заводятся командой, и это записано в рантбуке, а не
  подразумевается.
