# Spec: весь сервис поднимается одной командой

## Problem

`docker-compose.dev.yml` объявляет api, worker, postgres и redis с Ф1, но
пользуются им наполовину: сегодня Postgres поднят в докере, а uvicorn и vite
запущены на машине руками, миграции прогнаны третьей командой. Работает это
ровно у того, кто знает последовательность.

Проверка показала, почему так вышло: **образ никогда не собирался**. В корне нет
`.dockerignore`, а дев-стадия заканчивается `COPY . .` — в образ уезжают `.venv`
(319 МБ, собранный под macOS) и `node_modules` (372 МБ). Первая же сборка была бы
долгой, а получившийся контейнер — с нерабочим виртуальным окружением внутри.

Фронта в компоузе нет вовсе.

## In scope

- `.dockerignore`: в контекст сборки не уезжает ничего, что собрано на машине.
- Дев-стадии образа: питон отдельно, фронт отдельно (`node`), обе с горячей
  перезагрузкой через монтирование исходников.
- Сервис `web` в компоузе: vite на 5173, прокси `/api` на контейнер `api`
  (адрес приходит переменной, в коде его нет).
- Сервис `migrate`: `alembic upgrade head` одноразово, до старта api и worker.
- Проверки живости (`healthcheck`) у api: «поднялся» значит «отвечает», а не
  «процесс запущен».
- `docker compose up` поднимает всё; `README.internal.md` описывает это одной
  командой вместо трёх.

## Out of scope

- **Боевой компоуз и nginx** — следующая поставка (`docker-prod`).
- TLS, домен, секреты на сервере, бэкапы — Ф9 и настоящий сервер.
- Публикация образов в реестр: пока собираем на месте.
- Запуск тестов внутри контейнера: CI гоняет их своим способом, и дублировать
  его здесь значит завести вторую правду о том, как проходят гейты.

## Acceptance examples

| # | Вход | Ожидаемый выход |
|---|---|---|
| E1 | `docker compose -f docker-compose.dev.yml up -d` на чистой машине | поднимаются postgres, redis, migrate, api, worker, web |
| E2 | `curl localhost:8000/api/health` | `status: ok` и номер миграции — значит migrate отработал до api |
| E3 | открыть `localhost:5173` | форма входа; вход работает через прокси на контейнер `api` |
| E4 | правка файла в `src/` | api перезапускается сам, пересборка образа не нужна |
| E5 | правка файла в `web/src/` | экран обновляется сам |
| E6 | `docker compose build` | контекст без `.venv` и `node_modules` |
| E7 | `node_modules` машины (macOS) | не подменяет установленные в контейнере (Linux) |
| E8 | api поднят раньше базы | ждёт её готовности, а не падает с ошибкой соединения |

## Non-functional

- Ни одного адреса в коде: адрес api для прокси приходит переменной окружения.
- Дев-компоуз и боевой — **разные файлы**: смешивать их значит держать в одном
  месте два набора решений про секреты и порты (правило принято в Ф1).
- Поставка укладывается в `max_loc_diff` 800 без waiver.

## Open questions

- Версии node и python в образах прибиты цифрой. Их обновление — отдельное
  решение, а не побочный эффект пересборки.
