# Diagnosis: две кампании одного сайта дают в пачке один PDF (Z39)

## Симптом

У сайта с двумя хорошими или средними кампаниями пачка ZIP содержит один PDF,
`кейсы.csv` — одну строку, а обе строки `cases` ссылаются на один файл с одной
sha256 и несут одни и те же числа. Копия дев-базы 24.09.2026
(`cases_casepack_tests`): у `nordvpn.com` кампании 13039 (08.2024–07.2025) и
13040 (10.2025–09.2026) во всех десяти сборках — одинаковый файл, одинаковая
сумма и одинаковая подсветка «6 894 → 10 840 (+57 %)».

**Repro:** `tests/test_cases_pack.py::test_two_campaigns_get_two_files` — две
кампании одного домена, обе хорошие/средние, `pack_cases()`; в архиве должно
быть два PDF.

## Где домен служит ключом на пути пачки — все места

| Место | Что по домену | Следствие у двух кампаний |
|---|---|---|
| `cli/case_commands.pack_cases`: `numbered = {item.domain: …}` | номер сборки и кейс | вторая кампания затирает первую: в `pack` уходит один кейс |
| `pack_cases`: `blocked = {item.domain for item in bundle.skipped}` | отказ контент-запрета | запрет одной кампании снимает со строки `cases` обе |
| `pack_cases`: `numbered.get(item.domain, item.case)` в `store_case` | данные строки `cases` | обе строки получают подсветку, текст и анонимность одной кампании |
| `pack_cases`: `next(one.path … if one.domain == item.domain)` | путь артефакта | обе строки ссылаются на один файл |
| `export/archive.pack`: вход `(domain, case)`, исходы с `domain` | опознание исхода | исход пачки нельзя сопоставить с проектом иначе, чем доменом |
| `cases/builder._projects`: `order_by(Project.domain)` | порядок попыток | порядок двух кампаний не определён: «выживает» то одна, то другая |
| `cli/case_commands.render_case` | отбор по домену (`build_cases(domain=…)`) | не дефект: цикл по попыткам, номер и запись — по `attempt.project_id` |
| `api/routers/cases.py`, `export/removal.py`, `cases/freshness.py` | — | ключ — кейс, проект или sha256; домен не участвует |

## Гипотезы

- H1: дефект в разведении имён (`pdf_renderer.unique_name`) — второй файл
  затирает первый на диске → ОПРОВЕРГНУТА: `render_pdf` второй кампании при
  другом содержимом пишет «… (2).pdf» (правило 18а, `_same_content`); в
  каталоге выгрузки дев-стенда лежат и «nordvpn.com — Кейс.pdf», и «…
  (2).pdf». В архив второй файл не попадает потому, что до `pack` доходит одна
  кампания из двух.
- H2: `build_cases` отдаёт одну попытку на домен → ОПРОВЕРГНУТА: `_projects`
  берёт все проекты, `_attempt` — по одному на проект; прогон `cases --source
  fixture` на копии даёт «кейс собран: 67» при 60 PDF в пачке — две кампании
  `nordvpn.com` и две `zeta-clinic.example` среди собранных есть.
- H3: ключ по домену в `pack_cases` — словарь `numbered`, множество `blocked`
  и поиск пути → ПОДТВЕРЖДЕНА: на копии базы (`pack --source fixture`, код
  `origin/main`) «кейс собран: 67», «кейсов внутри: 60», «не попал» — 5 строк
  при шести запрещённых кампаниях; строки `cases` v11 кампаний 13039 и 13040 —
  один файл `nordvpn.com — Кейс v11.pdf`, sha256 `6d4c7936cbda…`.
- H4: чья кампания «выживает», решает порядок строк, и он случаен → ПОДТВЕРЖДЕНА:
  у `nordvpn.com` файл сборок 1, 3–5, 7, 9 — sha256 `772e2403…`, сборок 2, 6,
  8, 10 — `fa0123b3…`; `_projects` сортирует только по домену, а обновление
  строки проекта (статус после каждого прогона) переносит её в куче Postgres.

## Корневая причина

Домен в пачке служит опознанием кейса, хотя с 14.09.2026 (Z15) проект
опознаётся доменом **и периодом**. `pack` принимал пары «домен, кейс» и
возвращал исходы с доменом, поэтому `pack_cases` и не мог сопоставить файл с
проектом иначе — все три места ключа выросли из формы входа `pack`.

## Почему прошло мимо гейтов

Тесты архива (`test_cases_archive.py`) проверяют `pack` на разных доменах, а
путь «сборка → пачка → строка `cases`» целиком не проверял ни один тест: у
`pack_cases` не было оракула. Две кампании одного сайта на стенде появились
14.09.2026, и дефект виден только по базе. Усиление: W1–W5 идут через
настоящий `pack_cases` и сверяют архив со строками `cases` и `case_artifacts`.
