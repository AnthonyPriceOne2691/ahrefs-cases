# Diagnosis: журнал сборки кейсов — «собрано 0, пропущено 53» при десяти кейсах

## Симптом

Прод 24.09.2026: прогон ступени кейсов в журнале — «0 из 53, пропущено 53», в
раскрытии «записей по доменам нет: прогон не дошёл до сбора»; лог воркера —
«кейс собран: 10, не положен по группе: 41, данных не хватило: 2, вердикт не
про эти данные: 0; архив …; кейсов внутри: 10». Копия дев-базы (код ветки
`bugfix/two-campaigns-two-cases`, воркер RQ): после переклассификации по
фикстурным рядам сборка положила в пачку 61 кейс, журнал прогона 1839 — «0 из
75, пропущено 75», судеб 0; оповещение — «готов кейс zooplus.de — Кейс
v11.pdf». С вердиктами по живым рядам (сборка читает фикстурные) — пачки нет
вовсе, журнал тот же, оповещение — «готов кейс wineverygame.com — Кейс
v43.pdf».

**Repro:** `tests/test_cases_journal.py::test_cases_run_counts_and_names_every_project`
— сборка кнопкой по своим проектам: `projects_ok` 1 и судьба у каждого.

## Откуда журнал берёт числа ступени кейсов

| Число | Кто пишет | Что было у ступени кейсов |
|---|---|---|
| `projects_total` | `api/routers/runs._enqueue` — `count(Project)` при постановке в очередь | все проекты базы |
| `projects_ok`, `projects_failed`, статус | `collect/run_journal.finish_run` по строкам `run_items` | `finish_run` не зовёт никто: 0 и 0; статус `done` ставит `_run_guarded` |
| `projects_skipped` | `api/routers/runs._row` — вычитанием `total − ok − failed` | все проекты |
| судьбы | `run_journal.fates` по `run_items` | строк нет |
| сводка | `cli/case_commands.pack_cases` — `print` в лог воркера | в журнал не уходит: задача получает только код возврата, `_finish` для `done` пишет `error = ""` |

## Гипотезы

- H1: судьбы пишутся, но экран их не показывает → ОПРОВЕРГНУТА: `GET
  /api/runs/1839` на копии — `fates: []`, в `run_items` строк прогона 1839 нет
  (SQL); раскрытие честно говорит «записей нет».
- H2: `projects_ok` считает не тот исход → ОПРОВЕРГНУТА: `finish_run` для
  прогона ступени кейсов не вызывается вовсе — `_pack` зовёт `start_run` и
  `pack_cases()`, и больше ничего; `projects_ok` остаётся умолчанием 0.
- H3: знание о сборке теряется на границе задачи → ПОДТВЕРЖДЕНА: `pack_cases`
  собирает `CaseReport` и `Packed`, печатает их и возвращает `int`; у
  `_pack` нет ни исходов по проектам, ни пачки — записать нечего (класс L130).
- H4: хватит писать исходы старыми значениями перечисления → ОПРОВЕРГНУТА: слово
  исхода на экране берётся из значения (`status.RUN_ITEM_LABELS`), и «не
  положен по группе» пришлось бы выдать за «пропущен: строка не принята» или
  «нет данных» — новая неправда вместо старой.
- H5: новые строки `run_items` безвредны для остального → ОПРОВЕРГНУТА:
  `cache.empty_since` берёт последние строки проекта из журнала без различия
  ступени, и строка «данных не хватило» у пустого домена рвала бы цепочку «нет
  данных» — следующий сбор покупал бы пустоту заново (класс Z33, от 50 units за
  домен). Исходы ступени кейсов исключаются из подсчёта.
- H6: оповещение о пачке смотрит на пачку → ОПРОВЕРГНУТА: `_ready_bundle` берёт
  самый свежий `CaseArtifact` по `built_at` и называет его файл; на копии —
  «готов кейс wineverygame.com — Кейс v43.pdf» при пустом каталоге выгрузки.

## Корневая причина

Ступень кейсов подключили к журналу прогонов (B6: строка прогона, ступень,
время начала), но не к его строкам: сборка отдаёт наружу только код возврата,
а у задачи нет пути записать исходы. Журнал вычитает «пропущено» из числа
проектов и показывает ноль собранных — формально из своих данных, по существу
ложь. Оповещение — та же форма: читает то, что под рукой (артефакты), а не то,
о чём говорит (пачку).

## Почему прошло мимо гейтов

`test_journal_names_the_stage` проверял ступень и время начала, но не числа и
не судьбы; фикстура экрана B6 держит `projects_ok: 0, projects_skipped: 18` у
сборки кейсов как норму. Усиление: Y1 проверяет состояние прогона после задачи
по своим проектам, Y5 — что новые строки журнала не трогают деньги.
