# Diagnosis journal

**Симптом:** экран «Кейсы» на дев-стенде показывает пятьдесят строк при шести
проектах: `legal-partners.pl` версии 9, `greenhouse.co.uk` версии 8,
`finhelp.io` версии 9 — и те же домены ниже, версиями 8, 7, 6.
**Repro:** собрать кейсы несколько раз (`POST /api/runs/cases`), открыть `/cases`.

- H1: экран дублирует строки при перерисовке → проверил: `GET /api/cases?limit=50`
  отдаёт ровно те же пятьдесят строк — дело не в рендере → ОПРОВЕРГНУТА
- H2: сборка создаёт лишние кейсы вместо обновления → проверил: версии растут
  по одной за прогон, и это **проектное решение** (`store_case` пишет версию,
  не затирая прежнюю: прошлый кейс должен оставаться доступным) → ОПРОВЕРГНУТА
- H3: библиотека отдаёт историю, а спрашивают у неё свежее → проверил:
  `list_cases` сортирует по `created_at desc` и не группирует по проекту
  вовсе → ПОДТВЕРЖДЕНА

**Корневая причина:** выдача отвечала на вопрос «что когда собиралось», а экран
задаёт другой — «какой файл отправить клиенту». История и рабочий список
смешаны в одном ответе, и с каждым прогоном рабочий список разбавляется.

**Почему прошло мимо гейтов:** ни один оракул не знал, сколько строк на проект
ожидается — тест библиотеки проверял одну строку на одном кейсе, а при одной
сборке история и свежее совпадают. Дефект виден только после **нескольких**
прогонов, то есть на живом стенде. Оракул добавлен:
`test_library_shows_one_case_per_project` заводит вторую версию и требует,
чтобы по умолчанию вернулась одна.
