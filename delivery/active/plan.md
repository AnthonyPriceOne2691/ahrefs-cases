# Plan: проект можно удалить — и видно, что за ним уходит

Класс M, первая из двух поставок (API и бэкенд; экран — вторая).

## Approach

Карта зависимостей из исследования 24.09.2026 перепроверена по коду и схеме
(`migrations/versions/3459a03e3ba6_initial_schema.py`, `storage/models/`):
всё, что принадлежит проекту, стоит на `ON DELETE CASCADE` — `metric_points`,
`verdicts`, `cases`, `case_artifacts` через `cases`; `cases.verdict_id` —
`RESTRICT`, но проверка встаёт после каскада, поэтому `DELETE FROM projects`
проходит одним оператором. `run_items.project_id` — `SET NULL`, у `runs` и
`units_ledger` ссылки на проект нет. **Миграция не нужна**: права живут в коде
(`deps._GROUP_RIGHTS`), в базе только личные решения.

1. **Право.** `delete_projects` в `_GROUP_RIGHTS` у engineer и admin; справочник
   `/api/users/rights` и проверка личных решений подхватывают его сами. Вход и
   `/api/auth/me` отдают итог `rights_of_user`, а не набор группы: экран второй
   поставки строит кнопку по этому списку.
2. **Замки — `storage/locks.py`.** Ключ постановки прогона переезжает из
   `api/routers/runs.py` (им же берёт замок удаление: между проверкой «нет
   активных» и удалением прогон не встанет). Новый ключ — «работа пишет строки
   проектов»: задача очереди держит его разделяемо **на всё время работы**
   (сессионный замок на своём соединении, снимается закрытием соединения —
   и смертью процесса), пересчёт порогов — разделяемо на свою транзакцию;
   удаление пробует его исключительно и не ждёт.
3. **Удаление — `export/removal.py` + роутер проектов.** След проекта (числа по
   таблицам, пути и суммы артефактов) считается до удаления; `DELETE` одним
   оператором, коммит, **потом** файлы: только внутри каталога выгрузки, только
   если на путь не ссылается артефакт другого проекта (сверка по
   разрешённому пути, а не по строке). Предпросмотр — тот же след без удаления.
4. **Журнал.** Свёртка судеб ключует `project_id`, а у удалённого — домен
   строки; судьба несёт `project_deleted`.
5. **Пачка.** `newest_pack` переезжает в `export/archive.py`; пачка опознаёт
   свои кейсы **по sha256 содержимого** (правило 18а: имя кейс не опознаёт) —
   PDF внутри, чьей суммы нет ни у одного артефакта, принадлежал удалённому
   проекту. Состояние пачки говорит об этом, скачивание отвечает `409`.

## Уроки по затронутым путям (`archive/INDEX.md`)

- **L158** — «удалить» и «сохранить историю» — два удаления под одним
  действием: здесь история — журнал прогонов (`SET NULL`), а проект уходит
  целиком. **L159** — журнал, не показывающий, чей исход, не отвечает на свой
  вопрос: отсюда `project_deleted` в судьбе.
- **L13, L130** — исход сворачивается по проекту и доходит до человека;
  `_fold_by_project` по `project_id` сливал все удалённые проекты прогона в
  одну судьбу с чужим доменом и суммой units. **L125** — первопричина отказа:
  хвост задачи, упавший на удалённом проекте, переписал бы прогон в `failed`
  — замок работы не даёт хвосту упасть.
- **L111** — команда без области действия: удаление бьёт по одному id, не по
  домену.
- **L150** — домен не опознаёт проект: вторая кампания того же сайта не
  трогается, ключ удалённой судьбы — домен, и две удалённые кампании одного
  сайта в одном прогоне сольются (объявленная граница, Z41). **L151, L152** —
  перенос месяцев между кампаниями даёт каждой свои копии: удаление одной
  не уносит точек другой (D3).
- **L202** — журнал расхода — единственный след оплаты: не трогается ни
  каскадом, ни кодом. Гонка «удаление во время прогона» ровно его и ломала:
  `store_history` падал на FK раньше `record_spend`.
- **L88, L89** — у пачки есть получатель, и свежая берётся по времени файла;
  **L49** — пачка — место ревью: отдавать её с кейсом удалённого проекта
  нельзя. **L153** — совпадение решается по содержимому: пачка опознаёт кейсы
  по sha256, общий файл двух кейсов не стирается. **L92, L93** — не применимы:
  выдача версий не меняется. **L173, L174** — новых путей со словом под
  `/api/cases` нет; `/{project_id}/deletion` не спорит с `/{project_id}`.
- **L8, L80, L148** — дев-база общая: тесты удаляют только свои проекты
  (`gone.delete.example` и соседи) и свои версии порогов, сторож
  `stand_verdicts_survive_the_suite` остаётся зелёным. Прогон сьюта этой
  поставки идёт на копии базы (`cases_delete_tests`): 24.09.2026 два сьюта из
  соседних worktree на одной базе переписали вердикты стенда (см. verify).
- **L87** — поле, которое никто не пишет, читается как данные:
  `project_deleted` вычисляется из самой строки журнала, а не хранится.
- **L52, L59, L101, L205, L206** — право строкой, личное решение перекрывает
  группу в обе стороны, итог считает одна функция: `rights_of_user` и для
  проверки, и для `/me`.
- **L57, L64** — путь отказа проверяется тестом: `403`, `404`, `409` —
  нынешними именами статусов.
- **L63, L85** — у задачи свой процесс и свой цикл: замок работы берётся
  внутри задачи своим соединением, а не у вызывающего.
- **L74, L78** — выбор режима принадлежит конфигу: каталог выгрузки — только
  `config.export.output_dir`, не умолчание обработчика.
- **L187** — не применим: выдача журнала не растёт, список судеб ограничен
  прежним `MAX_FATES`. **L142** — реестр находок: строки ставятся номерами,
  закреплёнными координатором (Z39–Z41).

## Stack / boundaries

- `storage/locks.py` — ниже всех: замки нужны и `api`, и `workers`.
- `export/removal.py` — слой `export`: файлы кейсов и пачка — его артефакты;
  ядро не знает про FastAPI (`tests/test_core_isolation.py`).
- Роутеры — обвязка: замки, порядок «проверить → удалить → коммит → файлы»,
  тексты отказов.

## Rejected alternatives

- **Живость задачи через `workers/reaper.job_state` вместо замка** — отклонено,
  потому что при `QUEUE_BACKEND=inline` (тесты и дев) задачи в RQ нет вовсе:
  хвост идёт в потоке API, а RQ ответил бы «задачи нет» — то есть «можно
  удалять» посреди работы. Ещё и Redis в пути запроса удаления, и «не знаю»
  при его недоступности. Замок Postgres знает о живости сам и снимается смертью
  процесса.
- **Мягкое удаление (`projects.deleted_at`)** — отклонено владельцем
  («Удалять вместе»); вдобавок каждый `select(Project)` (смета, кандидаты,
  классификация, CLI — 16 мест) пришлось бы учить прятать удалённых.
- **Удалять явно, от детей к родителям (как `tests/owned_rows.delete_owned`)**
  — отклонено, потому что каскад уже стоит в схеме, а явный порядок обязан
  помнить `cases → verdicts` из-за `RESTRICT`: вторая копия правила, которая
  разойдётся со схемой при первой миграции.
- **Пересобирать пачку сразу после удаления** — отклонено: пересборка создаёт
  новую версию кейса каждому хорошему и среднему и строку в журнале прогонов,
  то есть тратит решение человека.
- **Опознавать кейсы пачки по домену из `кейсы.csv`** — отклонено, потому что
  у двух кампаний одного сайта домен один (правило 18а): удалив одну из них,
  пачка оставалась бы «чистой».
- **Замок работы и в CLI (`scripts/run_collect.py`)** — отложено: замок на всю
  команду делает базу обязательной и для команд, которые её не трогают
  (`intake` с нечитаемым источником проверяется без базы), а список «пишущих»
  команд — вторая копия знания. Граница объявлена (Z41).

## Risks

- Сессионный замок на пуле: вернувшееся в пул соединение унесло бы замок с
  собой. Замок берётся на своём движке без пула (`NullPool`, `AUTOCOMMIT`) и
  снимается закрытием соединения.
- Путь артефакта бывает относительным (`data/out/…` на дев-стенде) — разрешается
  от рабочего каталога процесса, как у скачивания; проверка «внутри каталога
  выгрузки» — по разрешённым путям.
- Файл может ссылаться сразу на два кейса (`render_pdf._same_content`, дефект
  `pack_cases`, Z39) — стирается только ничейный.

## Rollout / migration

Миграции нет. Право появляется у групп с выкаткой; экран его подпишет во
второй поставке — до неё справочник прав покажет ключ `delete_projects` как
есть.

## Test / eval strategy

- `tests/test_api_projects_delete.py` — D1–D11, D13 через HTTP на своих строках;
  D14 и замок пересчёта — пробой замка из соседнего соединения.
- `tests/test_jobs_mark_the_run.py` — прежние тесты метки не требуют базы:
  замок работы заглушается вместе с `_finish`.
- Исполнение на копии дев-базы (`cases_delete_check`): удаление проекта с
  кейсом, двумя кампаниями и историей в журнале, счётчики по таблицам до/после
  и файлы на диске — `eval-smoke.md`.
