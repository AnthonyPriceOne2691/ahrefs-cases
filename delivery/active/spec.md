# Spec: управление пользователями и точечные права

Поставка Ф5.5, по решению владельца: не ждать от заказчика список сотрудников с
группами, а дать администратору заводить людей и выдавать права самому.

## Problem

Сегодня пользователь заводится только командой в консоли на сервере. Это верно
для первого администратора и неверно для всех остальных: людей заводит
руководитель, а не инженер с доступом к машине.

Второе. Права сейчас определяются **только группой**, а группы три и различие у
них одно — правка порогов. Проект будет расти, и первое же новое право
(«кому можно запускать прогон», «кому видно расход») потребует либо четвёртой
группы, либо правки кода. В CRM агентства эта развилка уже пройдена: там роль
даёт набор прав, а **личные права у пользователя перекрывают роль** —
`user.permissions`. Берём этот приём: он позволяет выдать право одному человеку,
не заводя роль.

Третье, практическое: пароль. Заводя человека, руководитель не должен его
придумывать, а сервис не должен присылать его почтой — пароль **генерируется и
показывается один раз**.

## In scope

- `users.permissions` (JSONB) — личные права поверх роли; миграция.
- `POST /api/users` — завести человека: почта, имя, группа; пароль
  генерируется и возвращается **один раз**.
- `GET /api/users` — список с группой, активностью и личными правами.
- `PATCH /api/users/{id}` — сменить группу, включить/выключить, выдать или
  отобрать личное право.
- `POST /api/users/{id}/password` — перевыпустить пароль (показывается один раз).
- `POST /api/auth/password` — сменить **свой** пароль, зная старый.
- Защиты, перенесённые из CRM вместе с причинами: нельзя снять группу с
  последнего администратора, нельзя выключить себя, почта уникальна.

## Out of scope

- **Открытый bootstrap первого администратора через API** — в CRM он есть, но
  опирается на их флаг и окружение. У нас первый администратор заводится
  командой на сервере: лишняя дверь в интернет ради одноразового действия не
  нужна (урок L24 — переносить паттерн вместе с опорой).
- Почта с паролем, восстановление пароля, SSO — ТЗ не требует.
- Экран управления людьми — Ф6; здесь API.

## Acceptance examples

| # | Вход | Ожидаемый выход |
|---|---|---|
| E1 | `POST /api/users` пользователем | `403`: заводить людей — право `manage_users` |
| E2 | `POST /api/users` админом | `201` и пароль в ответе **один раз**; в базе только хеш |
| E3 | повторная почта | `409`: почта — логин, она уникальна |
| E4 | `GET /api/users` | список с группой, активностью и личными правами |
| E5 | выдача личного права пользователю | у него появляется право без смены группы; у остальных из группы — нет |
| E6 | отзыв личного права, которое даёт группа | право пропадает **у этого человека**: личное решение перекрывает групповое в обе стороны |
| E7 | снять группу с последнего администратора | `409` с причиной: система без администратора не управляется |
| E8 | выключить свою учётную запись | `409`: выключать себя нельзя, иначе дверь запирается изнутри |
| E9 | перевыпуск пароля | новый пароль в ответе один раз; старый перестаёт работать |
| E10 | смена своего пароля с неверным старым | `401`, и пароль не меняется |

## Non-functional

- Пароль генерируется `secrets`, а не `random`: предсказуемый генератор — это
  открытая дверь.
- Пароль не пишется в лог ни разу, включая создание и перевыпуск.
- Поставка укладывается в `max_loc_diff` 800 без waiver.

## Open questions

- Личные права выдаются строками из известного списка. Неизвестное имя права
  отвергается: право, которого не проверяет ни один роутер, — обещание.
