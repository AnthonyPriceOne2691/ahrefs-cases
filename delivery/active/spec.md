# Spec: Ф2б — экономия units

Вторая половина Ф2 из `docs/PHASES_V3.md`. Первая (Ф2а — приём списка и сбор на
фикстурах) в архиве: `delivery/archive/2026-09-10-f2a-intake-fixtures/`.

## Problem

Сбор работает и стоит дорого: каждый прогон перезапрашивает всю историю каждого
домена. На 100 проектах это ~5 000 условных units за прогон, и второй прогон по
тому же списку стоит столько же, сколько первый.

Заказчик назвал «стоимость запуска на 100 URL» метрикой успеха сервиса, а бюджет
первичного прогона — 10 000 units. Шесть-семь сотрудников из четырёх отделов
будут заказывать пересекающиеся списки минимум раз в месяц: без экономии второй
отдел платит за те же данные второй раз.

**Главный DoD всей Ф2 закрывается здесь:** повторный прогон не делает повторных
запросов за уже собранные месяцы.

## Users / stakeholders

Инженер (пишет), заказчик (платит). Первый видимый заказчику эффект: разница
между первым и вторым прогоном в journal'е units — то самое число, которым
меряется успех.

## In scope

- **`cache`** — закрытые месяцы неизменяемы: собранный январь не
  перезапрашивается никогда. Текущий (незакрытый) месяц — перезапрашивается.
- **Инкрементальный `date_from`** от последней сохранённой точки, а не от
  границы периода.
- **Дедупликация между прогонами**: домен, собранный по заказу одного отдела,
  обслуживается из базы для второго.
- **Single-flight по домену**: два одновременных прогона с общим доменом делают
  один запрос.
- **`budget`**: смета до запуска (с учётом кэша), строки-резервы в `UnitsLedger`
  при постановке в очередь, мягкий стоп по остатку.
- **`quota`**: preflight через `subscription-info/limits-and-usage` (0 units),
  **fail-closed** — не смогли узнать остаток, прогон не стартует.
- **Память о пустом ответе**: домен без истории не перезапрашивается каждым
  прогоном. Дыра найдена сверкой с CRM (там — `consecutive_zero_runs` и
  adaptive TTL); у нас достаточно помнить факт и дату пустого ответа.
- **Прерванный прогон не становится тратой**: результат каждой задачи пишется
  и коммитится по ходу (чекпойнт), а не одним махом в конце. Вместе с кэшем это
  даёт возобновление без отдельного механизма resume: следующий запуск видит
  уже собранное и докупает только остаток.
- **Полная обработка ошибок прогона**: неожиданное исключение в задаче не валит
  прогон; падение вне задач закрывает прогон статусом и причиной, а не оставляет
  его в `running`; предохранитель на серию ошибок (§5 документа реализации, до
  сих пор не реализованный нигде); CLI не показывает трассировку.
- **Реапер зависших прогонов**: строка в `running`, которую никто не завершит,
  держит резерв вечно. Паттерн переносится из CRM агентства
  (`article_generation/run_reaper.py`, SEOCRMLB-473), где это ловили дважды на
  проде: генерация #99 висела пятые сутки, run #23 финализировали руками через
  SQL. Изобретать заново нечего.
- **Шаг 2 воронки**: `keywords-history`, `refdomains-history` (+ DR под флагом)
  только по кандидатам в кейсы; «плохие» дорогих метрик не получают.
- Строки `kind=cached` в журнале: сколько запросов **не** сделано — это и есть
  предъявляемая экономия.

## Out of scope

- Классификация (Ф3). Кандидатов шага 2 отбирает грубый префильтр по трафику,
  и он **не** называется группой: настоящую группу с объяснением даёт Ф3 и
  переопределяет отбор.
- HTTP и очередь (Ф5). Резервы пишутся при постановке задачи, но саму очередь
  ставит Ф5 — здесь резерв создаётся вызовом планировщика.
- Экран расхода units (Ф6). Данные для него готовы уже сейчас, рисование — там.

## Acceptance (observable)

- [ ] второй прогон по тому же списку не запрашивает уже собранные месяцы
- [ ] смета до запуска учитывает, что часть месяцев уже в базе
- [ ] прогон не стартует, если остаток квоты неизвестен
- [ ] в журнале видно, сколько запросов сэкономлено кэшем
- [ ] шаг 2 не выполняется по проектам, которые в кейс не пойдут

## Acceptance examples

| # | Вход | Ожидаемый выход |
|---|---|---|
| C1 | два прогона подряд по 100 доменам, период работ закончился в прошлом месяце | во втором прогоне **ноль** запросов к провайдеру; `UnitsLedger` второго прогона — только строки `kind=cached`; счётчик вызовов провайдера сравнивается в тесте, а не «выглядит меньше» |
| C2 | в базе история по май включительно, период работ до августа | запрос ровно один, с `date_from = 2025-06-01`; за январь–май запросов нет |
| C3 | сегодня 15 сентября, в базе точка за 1 сентября | сентябрь перезапрашивается (месяц не закрыт), август и раньше — нет |
| C4 | два прогона стартуют одновременно, общий домен `d1.example.com` | провайдер вызван по этому домену **один** раз; оба прогона получают одинаковые точки и оба пишут свои `RunItem` |
| C5 | смета на 100 доменов, у 60 из них история уже собрана целиком | оценка сметы равна стоимости 40 запросов, а не 100; отклонение сметы от факта после прогона — не больше 10 % |
| C6 | остаток квоты 4 000 при `AHREFS_UNITS_MIN_LEFT=5000` | прогон не стартует, причина названа числом (сколько есть, сколько нужно) |
| C7 | endpoint квоты не ответил (таймаут, 500) | прогон **не** стартует: «не знаем остаток» трактуется как «не тратим», а не как «наверное, хватит» |
| C8 | два человека готовят прогоны по 100 доменов одновременно | смета второго видит остаток **минус резерв** первого; без этого «кнопка disabled при нехватке» защищает только первого нажавшего |
| C9 | 100 проектов, префильтр признал кандидатами 30 | шаг 2 делает запросы только по 30; по остальным 70 дорогих метрик нет ни в журнале, ни в базе |
| C10 | прогон, где половина месяцев из кэша | отчёт называет два числа: запросов сделано и запросов сэкономлено; второе больше нуля |
| C11 | прогон висит в `running` дольше порога (воркер убит, деплой посреди прогона) | реапер переводит его в `failed` с причиной, читаемой оператором, и резерв перестаёт занимать квоту; прогон, честно финишировавший между выборкой и апдейтом, свой статус **сохраняет** |
| C12 | провайдер бросает неожиданное исключение (`KeyError` в разборе ответа, а не наш `AhrefsUnavailableError`) | проект помечается `failed` с типом и текстом исключения, прогон **продолжается** и завершается `partial`; исключение записано в лог с доменом и endpoint'ом |
| C13 | падение вне задач: база отвалилась на записи точек | прогон закрывается статусом `failed`, причина в `Run.error`, исключение пробрасывается наружу (не проглатывается); строки в `running` не остаётся |
| C14 | подряд `COLLECT_BREAKER_MAX_FAILURES` неудач (Ahrefs лёг) | предохранитель останавливает прогон: оставшиеся задачи помечаются `skipped_aborted` с причиной, статус `failed`, в отчёте видно, сколько не выполнено. Оставшиеся домены **не** запрашиваются — при лежащем Ahrefs это трата units на таймауты |
| C15 | любая необработанная ошибка в CLI | одна внятная строка в stderr и код возврата, не трассировка; код различает «не прочитан источник» (2) и «прогон упал» (3) |
| C16 | прогон убит на 70-м домене из 100 (SIGKILL, деплой) | данные 69 собранных доменов **сохранены** и их units записаны; следующий запуск догружает только 31 недостающий, а не платит за сотню заново |
| C17 | домен, по которому Ahrefs не отдал историю, в списке следующего прогона | повторный запрос **не** делается, пока не истёк `AHREFS_EMPTY_RETRY_DAYS`; в журнале строка `cached` с причиной «пусто, проверено <дата>». Иначе десять молодых доменов в списке покупают пустоту каждый месяц |

## Non-functional

- Кэш опирается на `MetricPoint` — отдельного хранилища нет. Второе хранилище
  означало бы два источника правды о том, что уже куплено.
- Single-flight работает внутри процесса. Межпроцессная блокировка (Redis) —
  Ф5, вместе с очередью; до тех пор два воркера не запускаются.
- Fail-closed везде, где речь о квоте: любая неопределённость трактуется как
  запрет тратить.

## Open questions

- **Граница «закрытого» месяца** при `history_grouping=monthly`: Ahrefs может
  отдавать точку текущего месяца как незавершённую. До Ф7 считаем закрытыми все
  месяцы, кроме текущего календарного; проверить на живом ключе.
- Реальная стоимость запроса и глубина истории — Ф7. Смета до тех пор считается
  по объявленной модели, и её отклонение от факта станет наблюдаемой величиной.
