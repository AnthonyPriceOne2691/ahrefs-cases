# Spec: пороги по API и алерты

Последняя поставка Ф5. Фаза закрывается тем, ради чего ТЗ развело три группы
доступа: правкой порогов — и мониторингом units, который заказчик просил прямо.

## Problem

Пороги — самое опасное место сервиса: одна цифра перекладывает по группам всю
базу и меняет, какие кейсы уйдут клиентам. По ТЗ их утверждают Head of Link
Building и Owner, а пользователь править не может. Сейчас пороги живут файлом и
командой; ни сохранить новую версию, ни применить её из сервиса нельзя.

При этом **смотреть и применять — разные действия**: пересчёт бесплатный
(Ahrefs не дёргается), поэтому предпросмотр «кто сменит группу» доступен всем,
кто видит пороги, а сохранение и активация — только тем, у кого есть право.

Второе требование ТЗ: **мониторинг units с алертами**. Остаток квоты, упавший
прогон и готовая пачка кейсов — три состояния, о которых оператор должен
узнавать сам, а не выяснять.

## In scope

- `GET /api/rulesets` — версии порогов и какая активна (право `read`).
- `POST /api/rulesets` — сохранить **новую версию** (право `edit_thresholds`).
- `POST /api/rulesets/{version}/preview` — «кто сменит группу», без записи
  (право `read`: смотреть можно всем).
- `POST /api/rulesets/{version}/activate` — сделать действующей (право
  `edit_thresholds`).
- `POST /api/classify/recalc` — пересчёт по версии (право `edit_thresholds`).
- `GET /api/alerts` — остаток units, упавшие прогоны, готовая пачка.

## Out of scope

- **Отправка алертов в Telegram/Asana** — бонус ТЗ и внешняя интеграция; здесь
  сервис отвечает состоянием, а доставка приходит с настройкой каналов.
- Редактор порогов как экран — Ф6.
- Удаление версий: вердикты ссылаются на них, и версия обязана оставаться.

## Acceptance examples

| # | Вход | Ожидаемый выход |
|---|---|---|
| E1 | `POST /api/rulesets` пользователем | `403` с названием права: пороги ему закрыты |
| E2 | `POST /api/rulesets` админом | `201`, новая версия появилась и **не** стала активной сама |
| E3 | сохранение версии с тем же именем | `409`: версия неизменяема, иначе вердикты по ней перестанут объясняться |
| E4 | пороги, не проходящие проверку модели | `422` с причиной, а не сохранённый мусор |
| E5 | предпросмотр пользователем | `200`: смотреть можно всем, кто видит пороги |
| E6 | предпросмотр | ничего не записывает: вердикты после него те же |
| E7 | активация версии пользователем | `403`; админом — `200`, и активная версия сменилась |
| E8 | пересчёт админом | вердикты пересчитаны, Ahrefs не тронут |
| E9 | `GET /api/alerts` при остатке ниже порога | алерт про остаток units с числом |
| E10 | `GET /api/alerts` после упавшего прогона | алерт про прогон с его номером; нет поводов — пустой список, а не тишина |

## Non-functional

- Ни один вызов этой поставки не тратит units: пересчёт и предпросмотр
  бесплатны по построению.
- Версия порогов неизменяема: правка = новая версия.
- Поставка укладывается в `max_loc_diff` 800 без waiver.

## Open questions

- Порог алерта по остатку берётся из настроек (`AHREFS_UNITS_MIN_LEFT`), того
  же, что у мягкого стопа прогона. Разделить их можно, но пока это одно число:
  «мало units» означает одно и то же для прогона и для оператора.
