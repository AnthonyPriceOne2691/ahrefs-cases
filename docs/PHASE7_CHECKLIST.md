# Ф7: что проверить первым же живым ключом

Список составлен заранее, пока предположения свежи. Каждый пункт — гипотеза
из `docs/FINDINGS.md` с готовым способом проверки и с тем, что делать при
расхождении. Цель — закрыть все догадки об API за один заход, а не выяснять
их по одной в течение недели.

**Перед началом:** `AHREFS_PROVIDER=live` ставит человек, не агент
(`AGENTS.md`). Первые запросы делать по **одному** домену, не по списку.

---

## Шаг 1. Квота — бесплатно, поэтому первым (Z2)

```
GET /v3/subscription-info/limits-and-usage
```

- [x] Ответ содержит ключи `units_limit` и `units_usage`? — **нет, и это записано:**
      ответ вложен в `{limits_and_usage}`, поля называются `units_limit_api_key`,
      `units_usage_api_key`, `units_limit_workspace`, `units_usage_workspace`
      (Z2, опровергнута 10.09.2026; `collect/quota.py` читает именно их).
      Подтверждено 14.09.2026: остаток ключа 1 463 353, воркспейса 3 797 231.
- Если имена другие → поправить `_UNITS_LIMIT_KEY` / `_UNITS_USED_KEY` в
  `collect/quota.py`. Тест `test_quota_with_expected_keys_works` обновить на
  реальную форму.
- Признак, что этот пункт пропущен: `preflight` даёт `UNKNOWN` с текстом
  «в ответе нет ключа», и **ни один прогон не стартует**.

## Шаг 2. Форма history-ответа (Z3)

```
GET /v3/site-explorer/metrics-history?target=<домен>&date_from=2025-01-01
    &history_grouping=monthly&mode=subdomains&select=date,org_traffic,org_cost
```

- [x] Список лежит по ключу `metrics`? (`EndpointSpec.list_key`) — **да** (Z3, 10.09.2026)
- [x] В строке есть `date`, `org_traffic`, `org_cost`? — **да**
- [x] Формат даты — `2025-01-01T00:00:00Z`; разбор это умеет
- При расхождении правится **одна** запись в `collect/endpoints.py`; разбор
  строки один на все endpoint'ы (`live._to_point`).
- Признак пропуска: `AhrefsResponseError` с перечислением пришедших ключей.

Повторить для остальных пяти endpoint'ов — их `list_key` угаданы так же.

## Шаг 4. Сетка и глубина (H4, H3)

- [x] Все точки — первые числа месяцев? — **да** (H4, 10.09.2026)
- [x] Запросить `date_from` за 24 месяца: сколько пришло? — **33 из 33** (H3, с запасом)

- Если глубина меньше 24 — уменьшить `AHREFS_MAX_HISTORY_MONTHS` до реальной,

  (в вердикте это видно как `history_truncated`, но лучше не создавать случай).

## Шаг 5. Закрытый месяц (H2) и счётчик расхода (H8)

Два вопроса, которые нельзя закрыть одним заходом: нужен один и тот же домен в
два разных дня. Оба задаёт один инструмент — `scripts/probe_next_day.py`.

```
AHREFS_PROVIDER=live python3 scripts/probe_next_day.py ahrefs.com
```

Первый запуск снимает снимок (квота бесплатно + 50 units за домен), второй
через день-два сравнивает и называет вердикт. Снимки — в `data/raw/`, вне git.

- [x] **H2 — замерено 14.09.2026, ответ не бинарный.** Закрытые месяцы
      **меняются**, но на единицы визитов: июль 4 550 157 → 4 550 154 (−3),
      август 5 976 774 → 5 976 772 (−2), текущий сентябрь +2 298. Дрейф
      0,00007 % против порогов в десятки процентов — правило кэша остаётся,
      а допуск надо записать числом (H2 и Z13 в `docs/FINDINGS.md`).
      ~~Меняется~~
      закрытый → `cache.closed_through` обязан отступить на месяц дальше, иначе
      неполные данные останутся навсегда. Не меняется ничего → вопрос открыт, а
      не закрыт: повторить через несколько дней.
- [x] **H8 — закрыт 13.09.2026.** Счётчик реален (530 812 → 532 476 за сутки),
      но **отстаёт**: 50 units, потраченные минутами раньше, в нём не видны.
      Значит остаток из API — вчерашний, и `preflight` обязан вычитать из него
      собственный журнал за окно задержки. Проверять сдвиг бесплатно:
      `--quota-only` спрашивает только счётчик и снимка не пишет.

## Шаг 7. Batch-analysis: рычаг ежемесячного обновления (H6)

Отдельный замер, потому что он про **повторный** прогон, а не про первичный.
Минимум 50 units за запрос делает догруз одного месяца таким же дорогим, как
догруз восемнадцати: 5000 units на сотню доменов при каждом обновлении.

- [x] `POST /v3/batch-analysis/batch-analysis` (путь с повтором группы; без
      повтора — 404 за 0 units) на 5 целях, `select=org_traffic` — **50 units**.
      ~~Ожидаем~~
      55 units (5 строк × 11) — то есть построчный биллинг работает и здесь.
      Стоит замер 55 units, экономит потенциально 3900 на каждом обновлении.
- [x] Пришло 50 — сработал минимум. Повторено на **6 целях: 60 units**,
      `x-api-units-cost-row: 10`. Биллинг построчный; шести хватило вместо
      двадцати (60 units вместо 200). ~~Если пришло 50 — повторить на 20~~
      (ожидаем 220): на пяти целях минимум маскирует построчность.
- [x] Если цена не построчная — записать какая. **Не понадобилось: построчная,**
      10 units за строку с одним полем (5 целей — 50, 6 целей — 60).
      Тогда batch выгоден тем сильнее, чем больше целей, и упирается в 100.
- [x] Проверить, что в ответе **нет даты** — **подтверждено:** строка ответа
      содержит только `org_traffic` числом. Точка Б — только проектам с
      `period_end` в текущем месяце, точка А недостижима.
      Если параметр даты всё же существует — это меняет схему сбора целиком,
      и поставку про шаг 1 надо пересматривать, а не дополнять.
- [x] Записать, сколько проектов имеют `period_end` в текущем месяце —
      **ноль из сорока** на стенде (14.09.2026; самый свежий период кончается
      2025-12). Значит рычаг batch на этих данных не применим вовсе: он даёт
      срез «сейчас», а точка Б привязана к `period_end`, который задаёт
      агентство. Спросить заказчика, есть ли в боевом списке продолжающиеся
      кампании — от этого зависит, стоит ли вообще делать поставку под batch.
      ~~Записать, сколько проектов из реального списка имеют `period_end` в~~
      текущем месяце: только им batch даёт точку Б.
