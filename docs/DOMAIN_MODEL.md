# Главный домен

## Сущности

```
Project ──1:N──> MetricPoint            (серии метрик по датам)
   │
   ├──1:N──> CollectionRun ──1:N──> CollectionResult   (что реально дёрнули, сколько units)
   │
   ├──1:N──> Verdict                    (группа + score + объяснение, версия правил)
   │
   └──0:N──> Case ──1:N──> CaseArtifact (файл/страница экспорта)
```

### Project — центр домена
| Поле | Смысл |
|---|---|
| `id`, `domain` | нормализованный хост (без схемы/www, punycode → ascii) |
| `target_mode` | `subdomains` \| `prefix` \| `exact` — как считаем в Ahrefs (важно для проектов-разделов) |
| `period_start`, `period_end` | период работ; `period_end = null` = «по сегодня» |
| `niche`, `geo`, `client_ref` | опционально; `geo` = ISO-код страны для гео-разреза |
| `status` | `new` → `collecting` → `collected` → `classified` → `case_ready` \| `failed` \| `skipped` |
| `notes` | ручной контекст (сменился домен, был редизайн, штраф и т.п.) |

Инварианты: домен уникален в паре с `target_mode` и периодом; `period_start < period_end`;
проект без `period_start` не идёт в сбор (нечего считать точкой А).

### MetricPoint — сырая серия
`(project_id, metric, date, value, source, fetched_at)`.
`metric` — enum: `org_traffic`, `org_cost`, `kw_top3`, `kw_top4_10`, `kw_top11_plus`,
`refdomains`, `dr`, `pages`, `search_volume`. Одна строка = одна точка одной метрики.

Инвариант: `(project_id, metric, date, source)` уникально — повторный сбор
обновляет значение, а не плодит дубли (иначе графики врут, а units тратятся дважды).

### CollectionRun — прогон сбора
`status` (`queued`/`running`/`done`/`partial`/`failed`), `started_at`, `finished_at`,
`units_estimated`, `units_actual`, `projects_total/ok/failed`, `params_snapshot`
(grouping, набор метрик, версия клиента).

Смысл сущности: сбор — платная и падающая операция. Без журнала прогонов нельзя
ни объяснить счёт за units, ни докрутить упавшие проекты, ни доверять цифрам в кейсе.

### Verdict — классификация
`(project_id, ruleset_version, group, score, per_metric_reasons, decided_at, override_by)`.
`group` = `good` \| `medium` \| `poor` \| `insufficient_data`.

Две вещи, которые обязаны быть с самого начала:
- **`ruleset_version`** — пороги будут меняться; без версии старые вердикты
  становятся необъяснимыми, а перекалибровка — необратимой;
- **`insufficient_data` как отдельная группа**, а не «poor». Проект без истории
  и проект с плохим результатом — разные вещи, и путать их нельзя.

`override_by` — ручная переклассификация человеком (SEO-специалист видит контекст,
которого нет в цифрах).

### Case + CaseArtifact
`Case`: `project_id`, `verdict_id`, `template`, `point_a` / `point_b` (снимки метрик),
`highlights` (что подсветить), `narrative` (текст), `status` (`draft`/`in_review`/`approved`/`published`),
`anonymized` (bool — скрывать ли домен).
`CaseArtifact`: `format` (`html`/`pdf`/`docx`), `path`, `built_at`, `checksum`.

Инвариант: кейс генерится только для `group in (good, medium)` — но ручной
override может вытащить проект в кейс, и это должно быть видно в артефакте.

### Ruleset — версионированные пороги, редактируемые из UI
Пороги правит SEO-специалист, и правит часто (калибровка — процесс, а не разовая
настройка). Поэтому хранятся **в БД как версионированные записи**, а не в файле:

`Ruleset`: `version`, `payload` (само дерево порогов), `created_at`, `created_by`,
`is_active`, `note` («подняли порог трафика после калибровки на 80 доменах»).

Правила, без которых редактирование из UI превращается в проблему:
- **новая версия, а не правка на месте.** Сохранение порогов создаёт новую запись;
  прошлые вердикты остаются привязанными к своей версии и остаются объяснимыми;
- **активна одна версия** — она применяется к новым прогонам классификации;
- **вердикт хранит `ruleset_version`**, а кейс — вердикт. Иначе через месяц на
  вопрос «почему тут написано medium» ответить нечем;
- **пересчёт — явное действие.** Смена порогов не переписывает молча уже
  сгенерированные кейсы: UI показывает «N проектов сменят группу», пересчёт
  запускается кнопкой. Классификация бесплатна (API не дёргается), так что
  пересчитывать можно сколько угодно;
- файл порогов остаётся **сидом дефолтов** для первого запуска и справочным
  описанием структуры, а не источником истины.

## Стадии пайплайна

| Стадия | Идемпотентность | Стоимость |
|---|---|---|
| `intake` | да — повторная загрузка того же CSV не создаёт дублей | 0 |
| `collect` | да — по `(project, metric, date)` + кэш ответов | **платит units** |
| `classify` | да — чистая функция от серий + ruleset | 0 |
| `generate` | да — детерминированно, кроме LLM-текста | 0 или токены LLM |
| `export` | да — перерендер из тех же данных | 0 |

Главное архитектурное следствие: **`collect` отделён от всего остального**.
Классификацию и генерацию можно прогонять сто раз на уже собранных данных, не
трогая Ahrefs. Пороги будут калиброваться итеративно — если классификация тянет
API, каждая итерация стоит денег.

## Расчёт точки А → точки Б

Не «первое и последнее значение серии», а:

- **точка А** — среднее за окно (напр. 1–3 месяца) вокруг `period_start`,
  чтобы случайный выброс не сделал рост из ничего;
- **точка Б** — среднее за такое же окно у `period_end`;
- **дельта** — и абсолютная, и относительная: `+1200 визитов` и `+340%` — разные
  истории, и порог должен смотреть на обе (иначе сайт 10 → 40 визитов попадёт в «отличный кейс»);
- **опорная база** — по чему сравниваем: предыдущий период или YoY. Сезонные
  ниши (туризм, e-commerce) без YoY дают ложный рост.
